KAFKA - Notes (from L19_Kafka_Notes.pdf, TechByAni HLD-Notes)

The IPL example motivates the whole lesson. A producer sends every ball update from a CSK vs RCB match, like match_id 101, over 12.3, batsman Kohli, runs 4, straight to a consumer system that includes a scoreboard service, commentary engine, ML prediction system, analytics service, and notifications. The naive way to build this is the Amazon-order style fanout, where an Order Service directly calls Payment Service, Notification Service, Analytics Service, and Inventory Service. That breaks fast. Each new consumer means modifying the producer's code. It creates tight coupling, so any consumer failure blocks the producer. Retry logic becomes messy when one service is down. You get a scalability nightmare, no replay capability, no async processing, and real problems with ordering, data loss, retry failures, and backpressure. If instead consumers poll a database for updates, you get polling delay that isn't real time, high load on the database, ordering problems, and the fundamental ceiling that databases handle writes per second in the thousands, not the millions a big system like this eventually needs.

The fix is a durable queue sitting between producer and consumers, so the producer just appends events and consumers read independently. To scale that, you add more partitions so writes spread out. To manage ordering while scaling, you partition by something meaningful, like by team, so that all events for a given match stay in order within their own partition while different matches can be processed in parallel by a consumer group. This same shape generalizes to separate topics entirely, like a Women's IPL topic and a Men's IPL topic, each with its own partitions and its own consumer group.

What Kafka actually is: Apache Kafka is an open-source distributed event streaming platform. It can be used as a message queue or a stream processing system. It's designed for building real-time data pipelines and streaming applications, meaning it helps systems send, store, and process data continuously in real time.

Why Kafka exists: before Kafka, systems used point-to-point messaging like RabbitMQ or polling-based APIs. In large-scale systems like LinkedIn, Uber, Netflix, or Amazon, these patterns break down. Kafka solves scalability by handling millions of messages per second, durability by persisting data to disk and replicating it, fault tolerance by surviving broker failures, and it gives high throughput plus low latency.

Core components. A Producer sends messages, called events, to Kafka topics. Each event is a record, structured like key, value, timestamp - for example key is match_id_1, value is "Virat Kohli hits a 4", timestamp is the ISO time. Important producer details: the key determines which partition the message goes to - if key is match_id_1, all events for that same match go to the same partition, preserving ordering. Acks (acknowledgment levels) control durability: acks=0 is fire and forget, acks=1 waits for the leader to ack, acks=all waits for all in-sync replicas to confirm and is the safest. Idempotent producers prevent duplicate events even under retries.

A Topic is like a folder or category where messages of a specific type are stored - basically a logical grouping of partitions. Examples: match-events, user-notifications, orders, payments. Each topic is divided into multiple partitions for scalability - e.g. topic match-events has Partition 0, Partition 1, Partition 2.

A Partition is an ordered, immutable sequence of messages. Messages are continuously appended like a log file. Each message in a partition gets an offset, a unique incremental ID. Ordering is guaranteed only within a partition, not across the whole topic. This is what gives parallelism: consumers read different partitions in parallel.

A Broker is a server that stores data and handles producer/consumer requests. A Kafka cluster is multiple brokers. Example: Broker 1 holds Partitions 0 and 3, Broker 2 holds Partitions 1 and 4, Broker 3 holds Partitions 2 and 5. Each partition has a Leader replica that handles all reads and writes, and Follower replicas that copy data from the leader. If the leader fails, one follower becomes the new leader automatically (automatic failover). Each partition can be replicated across multiple brokers.

A Consumer pulls messages from Kafka - it is not pushed to. You control the offset, meaning where to start reading: auto offset (latest or earliest), or manual commit for precise control. Example: a consumer reading the match-events topic, Partition 0, from offset 1000 to 1200.

A Consumer Group is a set of consumers working together on a topic. Kafka guarantees that each partition is consumed by only one consumer within a single group. Relationship overview: one topic has multiple partitions (that's what gives parallelism). Within one consumer group, one partition is consumed by exactly one consumer. Across different consumer groups, each group can read the same partition independently - so two totally separate groups (e.g. Scoreboard service and Analytics service) can both consume from the same partition without interfering with each other. A consumer group collectively consumes multiple partitions. One consumer can read from multiple partitions if there are more partitions than consumers in the group.

Offset: each message in a partition has an offset, a monotonically increasing number. Consumers track offsets to know where they left off.

Replication: to ensure durability, each partition has replicas (a leader plus followers). Example with replication factor 3: Broker 1 is Leader for Partition 0, Broker 2 and Broker 3 are Followers for Partition 0. If Broker 1 dies, Kafka promotes one follower to leader.

Delivery semantics - Kafka provides three guarantees. At most once: messages may be lost but are never redelivered. At least once: no loss, but duplicates are possible. Exactly once: no loss and no duplicates, but this requires idempotent producers plus transactional writes.

The full end-to-end message flow lifecycle: Producer sends a record with topic, key, value, timestamp (e.g. topic match-events, key match_id_101, value "Virat Kohli hits a SIX!"). Then partition selection happens: Kafka decides which partition gets the message based on the key. If a key is present, the logic is hash(key) % num_partitions, so all same keys go to the same partition and ordering is preserved. If no key is present, Kafka uses round robin to spread messages evenly across partitions. Example: hash("match_id_101") % 3 = 1, so it goes to Partition 1. Ordering is only guaranteed within the same partition.

Next is broker assignment. Once the partition is determined, Kafka identifies which broker holds that partition. The mapping of partitions to brokers is managed by Kafka cluster metadata, maintained by the Kafka controller, a role within the broker cluster. The producer uses this metadata to send the message directly to the broker that hosts the leader of the target partition. Earlier, Kafka used ZooKeeper to store this cluster metadata and help elect the controller. Now, modern Kafka uses its internal KRaft (Kafka Raft) system, so ZooKeeper is no longer needed - KRaft manages all metadata and leader elections inside Kafka itself, using the Raft consensus protocol.

Then the broker (leader partition) writes the message. Each partition has a Leader Replica that handles all reads and writes, and Follower Replicas that copy data from the leader. Steps: the producer sends the message to the leader broker, the broker appends it to the partition's commit log, the message is given an offset (a unique ID), and the broker acknowledges the producer based on the acks configuration - acks=0 means no confirmation (fastest but riskiest), acks=1 means only the leader confirms, acks=all means all in-sync replicas confirm (safest).

Then replication happens in parallel with that write step, copying the message to the followers.

Then consumers read messages. Consumers belong to a Consumer Group. Each group reads from the topic's partitions, and each partition is read by exactly one consumer within that group. Steps: consumer sends a fetch request to the broker that is leader of the partition, the broker returns messages in batches, the consumer processes them (e.g. updates a database, updates the UI), and the consumer commits its offset after processing.

Then offset management: each message in a Kafka partition is assigned a unique offset, a sequential identifier indicating the message's position within that partition. Offsets are monotonically increasing and start from 0. This offset is what consumers use to track their progress while reading messages. As consumers read messages, they maintain their current offset. They periodically commit this offset back to Kafka, to the internal topic __consumer_offsets. If a consumer fails or restarts, it can resume reading from the last committed offset, instead of starting from the beginning.

Full lifecycle chain, top to bottom: Producer, then Partition Determination, then Broker Assignment (ZooKeeper in old Kafka / KRaft in new Kafka), then Leader writes message, then Followers replicate, then Consumers fetch, then Offsets committed. Properties achieved: fault-tolerant, ordered within partition, real-time and scalable.

When to use Kafka. Apache Kafka can serve two major purposes - it can act as a message queue or as a streaming platform. The difference depends on how data is consumed by your services. In a message queue, consumers pull messages when they're ready, one at a time - like filling a bucket from a tap, where you decide when to collect water. In a streaming model, data flows continuously, and consumers process it in real time - much like standing under a waterfall, where water keeps coming nonstop.

Kafka as a Message Queue: Kafka behaves like a traditional message queue when you want to handle asynchronous tasks, preserve event ordering, or decouple producers and consumers. Unlike RabbitMQ, Kafka is built for very high throughput and massive scalability. If your system needs to handle hundreds of thousands or millions of messages per second, Kafka is the right fit. For smaller workloads or low-latency, simple background tasks, RabbitMQ or SQS might be lighter and easier to manage.

Use Kafka as a message queue when: (1) You have tasks that can be processed asynchronously. Example, Amazon Order Processing System: when a user places an order, you confirm it instantly, but publish an event to a Kafka topic for background work such as sending an email, charging the card, or updating inventory - these tasks are handled asynchronously by different consumers. (2) You need to process events in strict order. Example, Cricket Ball-by-Ball Feed: each ball event ("Ball 1: Dot", "Ball 2: FOUR", "Ball 3: OUT") must be processed in the exact sequence they occur for that match. Kafka ensures ordering within a partition, so all events for a given Match ID are processed sequentially and correctly. (3) You want to decouple producers and consumers. Example, e-commerce microservices: the Order Service may produce events much faster than the Shipping Service can handle them. Kafka acts as a buffer between the two, letting each service scale independently and preventing one slow consumer from affecting the rest of the system.

Throughput note from the deck: for very high throughput or scalable, distributed processing, use Kafka. For lightweight, low-volume, low-latency workloads, a simple queue like RabbitMQ or SQS might be better suited.

Kafka as a Streaming Platform: Kafka shines as a real-time data streaming platform when you need to process information continuously as it arrives. Use Kafka as a stream when: (1) You need continuous, real-time processing. Example, ride-sharing platform like Uber: drivers send location updates every few seconds; Kafka Streams or Flink can consume these events to calculate ETAs, match riders with nearby drivers, and adjust surge pricing, all in real time. (2) Multiple consumers need the same data simultaneously. Example, online food delivery app like Swiggy or Zomato: every "order status update" (food prepared, out for delivery, delivered) is published to a Kafka topic. Multiple systems - the customer app, restaurant dashboard, and delivery tracker - can all consume this same stream of updates independently and simultaneously.

Interview tip from the deck: when asked "When would you use Kafka?", you can answer that Kafka can act as both a message queue and a streaming system. As a queue, it's great for asynchronous or ordered processing, like handling Amazon orders or ball-by-ball cricket events, especially when you need high throughput. As a stream, it's ideal for real-time use cases, like tracking drivers or broadcasting live order updates to multiple systems.

Scalability. A Kafka broker is just one server in a Kafka cluster that stores data and handles reads/writes. Kafka doesn't have a fixed message size limit - you can change it using message.max.bytes - but for best performance, keep your messages small, under 1 MB. Small messages mean faster processing, less memory pressure, and better network speed. Don't store big files or videos in Kafka. Instead, store large data like videos or PDFs in storage systems such as S3, and send only a small Kafka message containing the file's location.

Rough capacity estimate on decent hardware: one broker can store about 1 TB of data, and can handle roughly 1 million messages per second, depending on hardware and message size. If your total load fits within that, you may not even need to worry about scaling.

When you need to scale, there are two main ways: add more brokers (horizontal scaling), or use a smart partitioning strategy. Scaling in Kafka mostly depends on how you partition your data. Each message goes to a partition based on its key: partition = hash(key) % number_of_partitions. A good key choice gives even load; a bad key choice creates "hot partitions" where one partition gets all the traffic. Example: if you partition by ad_id and one ad goes viral, that single partition becomes overloaded - that's called a hot partition.

How to handle hot partitions, in order of preference: (1) Compound keys, the best practice - instead of using a single key like ad_id, combine it with another field, for example ad_id plus region, or ad_id plus user_id. This spreads messages more evenly while still keeping them logically grouped, e.g. traffic for different regions or users goes to different partitions. (2) Salting the key - add a random number or timestamp to your key, like "ad_id_01", "ad_id_02". This breaks heavy traffic for one key into multiple partitions. It's simple and effective, though it can make aggregation logic more complex later. (3) Random partitioning with no key - if message ordering isn't important, send messages without a key; Kafka will automatically assign partitions in a round-robin fashion. This guarantees even distribution across partitions, but you lose order within a topic. (4) Backpressure, the last resort - if producers are overwhelming Kafka, slow them down temporarily. Either limit the producer's send rate, or let managed services like AWS MSK throttle automatically. This gives brokers time to recover and prevents message lag buildup.

Fault tolerance and durability. Kafka is designed to never lose data. It does this through replication. Each partition is copied across multiple brokers: one broker is the Leader, the others are Followers. When a producer sends a message: it's written to the leader, the leader replicates it to all followers, and once all replicas confirm, the message is marked as "safe" - this depends on the producer's acks setting.

When a consumer fails. Kafka is usually "always available," but consumers can fail. Offset management: each message in a partition has an offset, like a line number. After processing, the consumer commits its latest offset to Kafka. If it crashes, it restarts from that saved offset - no data loss or duplication.

Rebalancing: in Kafka, multiple consumers can share the work by forming a consumer group. Each consumer in the group reads messages from a different set of partitions. If one consumer stops working - maybe it crashes, disconnects, or shuts down - Kafka automatically detects this and reassigns that consumer's partitions to the others in the group. This way, the remaining consumers pick up the extra work, and message processing continues smoothly without any data being left behind.

Handling retries and errors. Producer retries: sometimes messages fail to reach Kafka due to network or broker issues. Kafka supports automatic retries. Example config: retry: { retries: 5, initialRetryTime: 100 }, idempotent: true - idempotent: true ensures no duplicates even during retries.

Consumer retries: Kafka doesn't have built-in retries for consumers. You build your own system using a retry topic, to reprocess failed messages later, and a Dead Letter Queue (DLQ), to store permanently failed messages for investigation.

Performance tips from the deck: batch messages, compress data, choose balanced partition keys.

Retention. Kafka doesn't store messages permanently - it keeps them only for a limited time or until a certain amount of data is reached. You control this using two settings: retention.ms controls how long messages should be kept (time-based), retention.bytes controls how much data can be stored before older messages are deleted (size-based). By default, Kafka keeps messages for 7 days. You can increase this period if your system needs older data, but remember - the longer you retain messages, the more storage space and disk cost you'll need.
